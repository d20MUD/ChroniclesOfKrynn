## Review and identity

The release candidate is generated by `scripts/package_clan_release.py` only
after `scripts/validate_clan_release.py` reports success. Its `manifest.json`
identifies the MUD and web base commits, exact source overlay hashes, binary and
gateway/browser hashes, SQL/catalog/help inputs and validation logs. The base
commits alone do not identify these currently uncommitted changes. Review the
source overlays and tracked patches together; verify every manifest hash before
using the artifacts. Commit/tag the reviewed source as part of the actual release
process, then regenerate and revalidate if any source or build input changes.

There is no clan-specific approval automation in this repository. The generic
`scripts/deploy.sh` provisions a new installation and is not a clan migration or
approval mechanism. The concrete release decision requires the operator/reviewer
to record: reviewed artifact manifest/hash, Phase 51 mathematical pacing decision,
trusted policy/bootstrap implementation, target host/database/services, backup
locations and restore proof, maintenance window, rollback owner, and explicit
authorization for each migration, service restart and enablement step. None of
those approvals is implied by preparing this candidate.

  remaining operation IDs; never clear their locks or delete their journals.
- [ ] Take a coherent backup of the entire game SQL database (including triggers)
  and player/inventory files at the same quiesced point. Include clan/claim legacy

  Store credentials separately with restricted access. Record checksums and
  verify a restore to a separate staging database and file tree.

  treasury, relationships/zone claims, Favor, Clan XP/Influence, contribution

## Monitoring and rollback

Watch SQL errors and commit-unknown responses; boot authority/readiness;
accepted/pending operation age and recovery failures; distinct receipt/event and
account/week/family keys; XP/Influence/Favor ledger reconciliation; stale/private
MSDP state; HP/effect removal; world target availability; and gold/bound-item
checkpoint consistency. Alert and pause new progression work on duplicate
awards, unexplained balance drift, missing retention guards or invalid proofs.

The first response is a reviewed policy disable with SQL authority retained.
Runtime invalidation must recalculate/clamp Vitality HP, stop new effects/awards,
and preserve earned balances, deadlines, receipts and recoverable purchases.
Feature-off is not permission to discard already accepted economic operations.

Before any post-cutover SQL write, a full coherent pre-cutover restore may be
possible while writers remain stopped. After any SQL-authoritative write, do
not switch to legacy, reimport old files, restore SQL alone or install a binary
that cannot read current receipts/player codecs. Quiesce again; preserve the
current DB/files for diagnosis; prefer a compatible forward fix or supported
feature-disable. If a restore is authorized, restore the matching SQL and
player/inventory checkpoint together to an isolated target first, verify all
post-cutover receipt/timer/claim/binding state and exactly-once recovery, then
perform the separately approved recovery plan. Record any lost writes explicitly.

Mark release complete only after the approved deployment and verification on the
actual target are recorded. A generated package or passing local test is not a
deployed release.
